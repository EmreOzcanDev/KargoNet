# Phase 5 — UI Design Contract

> Visual and interaction contract for the two Phase 5 apps: `src/Web/Portal.Web` (ASP.NET Core MVC, Bootstrap) and `src/Web/operator-ui` (Angular 22 SPA). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Consistent with locked decisions D1–D8 in `05-CONTEXT.md`; none of them are re-opened here.

## Design System

Two apps, two stacks — one shared visual language (system fonts, same scale/colors below).

| Property | Portal.Web | operator-ui |
|----------|-----------|-------------|
| Tool | Bootstrap 5.3.3 (already bundled in `wwwroot/lib/bootstrap`; no install step) | none (manual SCSS, standalone components) |
| Preset | not applicable | not applicable |
| Component library | Bootstrap CSS utilities + classes only (no JS components beyond the already-bundled navbar collapse) | Angular standalone components authored in `src/app` |
| Icon library | none (text-only badges and buttons) | none (text-only badges and buttons) |
| Font | Bootstrap system font stack (no web font) | Same system font stack declared in `src/styles.scss` for visual parity |

Defaults resolved (no upstream answer, logged here):

- **No icon library in either app** — status is conveyed by badge text + color, actions by labeled buttons.
- **No web fonts** — system stack in both apps; keeps zero extra assets and matches Bootstrap's default.
- **operator-ui has no CSS framework** — layout via Bootstrap-style utility discipline manually (flex rows, `gap: 16px`, table classes) in `styles.scss`/component SCSS. Do not add a framework dependency.
- **`@microsoft/signalr` is NOT currently in `operator-ui/package.json`** — the plan must add it (v10.x) for D4/D5.
- **Navbar (portal):** keep the scaffolded light navbar; brand text changes from `Portal.Web` to `KargoNet`; nav links are Home and Create shipment (no Privacy link in the final app — scaffold leftover, safe default: remove).

### Status badge map (single source of truth)

Same semantic color in both apps (portal `bg-*` classes; operator `statuses.ts` → SCSS classes). 1:1 with the 7-value enum:

| Status | Badge variant | Hex |
|--------|--------------|-----|
| Created | light (bordered) | `#f8f9fa` bg / `#6c757d` text |
| PickedUp | secondary | `#6c757d` |
| InTransit | primary | `#0d6efd` |
| AtHub | warning | `#ffc107` / dark text |
| OutForDelivery | info | `#0dcaf0` / dark text |

In operator-ui the map lives in `src/app/core/statuses.ts` (`STATUS_OPTIONS: readonly string[]` + `STATUS_BADGE_CLASS: Record<string, string>`), per D6 — never hardcoded in templates. The portal renders the same variant server-side from the status string in a shared `_StatusBadge.cshtml` partial (no C# enum, per D6).

## Screen Specifications

### Portal.Web (server-rendered; `PortalApiClient` per D2)

Shared layout: navbar (brand `KargoNet`, links: Home, Create shipment), container, footer. All API access through `PortalApiClient` (`GetTrackingAsync`, `GetTimelineAsync`, `CreateShipmentAsync`); 404 → not-found view state, 5xx/timeout → dismissible error banner (D8). Server-rendered pages block on the API call, so there is **no client-side loading state on the portal** — the rendered page is the result (resolved default, logged).

#### Screen P1 — Home `/` (CUST-02 entry point)
- **Layout:** centered card (max-width 560px, `3xl` top spacing): page title `Track your shipment` (display role), form with label `Tracking number`, text input (`form-control`), primary button `Track shipment`; below: muted link `Create shipment` → `/shipments/new`.
- **Data source:** none (static).
- **Interaction:** GET form to `/track?number={input}`; empty input submits to `/track` (renders empty state).
- **States:** populated only.
- **Acceptance (CUST-02 entry):** form submits to `/track?number=`; brand reads `KargoNet`; create link present.

#### Screen P2 — Track `/track?number=` (CUST-02, CUST-03)
- **Layout:**
  - **Found:** status card (`.card`): card-header with tracking number (accent link, monospace-ish `font-family` not required — default face, weight 600); card-body as definition list: `Description` (or `—`), `Destination`, `Status` (badge from map), `Created` / `Updated` (timestamp format above). Below (`2xl` gap): timeline panel (`.card` with `#f8f9fa` header `Timeline`), rows in `occurredAt` ascending order: icon dot + `lg` row padding, label, badge, right-aligned timestamp.
  - **Empty (no number):** centered card with empty-state heading/body.
  - **Not found:** `alert alert-danger` with heading + body from copy contract, plus link `Back to home`.
  - **Error (5xx/timeout):** dismissible `alert alert-danger` + empty-state card.
- **Data source:** `GET {TrackingApiUrl}/api/tracking/{n}` → status card; `GET {TrackingApiUrl}/api/tracking/{n}/events` → timeline (both in one server request; timeline fetch failure with a successful status fetch renders the card + timeline error text, not a page failure).
- **Interaction:** timeline rows parsed from `payloadJson` (`shipment.created` → created row; `shipment.status.changed` → status row); `payloadJson` parse failures render the row with `eventType` text only (no crash).
- **States:** empty / found / not-found / error (no client loading state — server-rendered).
- **Acceptance:** CUST-02: unknown number shows `No shipment found for {number}`; known number shows the card. CUST-03: card shows all 6 `TrackingDto` fields; timeline shows created row + one row per status change in `occurredAt` order with timestamps.

#### Screen P3 — New shipment `/shipments/new` (CUST-01)
- **Layout:** card (max-width 560px): title `Create shipment`; fields: `Tracking number` (optional, hint `Leave blank to auto-generate.`), `Description` (optional), `Destination` (required); primary submit `Create shipment`. Validation summary (`alert alert-danger`) above the form on failure; jQuery unobtrusive client-side for the required destination.
- **Data source:** `POST {ShipmentApiUrl}/api/shipments` (`CreateShipmentRequest`).
- **Interaction:** success → 302 redirect to `/track?number={trackingNumber from ShipmentDto}` (the track page renders the result — no separate success screen). Validation failure (400) → re-render form with submitted values + summary. API 5xx/timeout → dismissible error banner, form preserved.
- **States:** populated form / validation error / API error.
- **Acceptance (CUST-01):** form posts all three fields; destination required (client + server); success lands on `/track` showing the created shipment with auto-generated number when omitted.

### operator-ui (Angular 22 SPA, `--ssr false`, standalone components)

Shared shell: `ShipmentsComponent` renders the whole page — header row (title `KargoNet Operator` + connection indicator) then content. One `TrackingService` per D4 (single `SignalR` connection, created in component `ngOnInit`, disposed on destroy, default auto-reconnect policy).

#### Screen O1 — Shipments list `/` (OPS-01, OPS-02, OPS-03)
- **Layout:** header (`.page-title` + right-aligned connection indicator: pill `Live` / `Reconnecting…` / `Offline` with success/secondary/danger color); table (`table table-striped` equivalent in SCSS), columns: `Tracking number` (accent link — opens the drawer, same target as `Timeline`), `Description` (or `—`), `Destination`, `Status` (badge from `statuses.ts`), `Updated` (timestamp format), `Actions`: status `<select>` (the 7 values from `STATUS_OPTIONS`, current status preselected) + `Apply` button + `Timeline` outline button. Row height comfortable (`md` cell padding); actions wrap on narrow widths.
- **Data source:** initial load `GET {shipmentApiUrl}/api/shipments` (environment.ts, D7). Live: `ShipmentUpdated` from the hub — patch the matching row in place (badge, `updatedAt`); append a new row (top) when an unknown tracking number arrives.
- **Interaction:**
  - `Apply`: `PUT {shipmentApiUrl}/api/shipments/{id}/status` with the selected status; on success the row's badge updates (the hub broadcast normally confirms it — patch locally on 200 if no broadcast arrives within the same tick); select resets to the new status. On 4xx/5xx: inline error `Couldn't update status — try again.` under the row, select keeps the user's choice.
  - `Timeline` (or tracking-number link): opens `TimelineDrawer` for that number (in-page component, D3/D5).
- **States:** loading (full-table: spinner + `Loading shipments…`); empty (`No shipments` + body, no table header); error (dismissible banner + empty area, retry = page reload affordance via banner link `Retry` — safe default: banner has a `Retry` link that re-runs the fetch); populated; per-row apply error.
- **Connection indicator:** `connected` → `Live` (success), `reconnecting` → `Reconnecting…` (secondary), `disconnected` → `Offline` (danger), driven by hub `stateChanged` events.
- **Acceptance:** OPS-01: table renders all shipments with badge per the status map. OPS-02: select → `Apply` posts `PUT /api/shipments/{id}/status` and the badge reflects the new status. OPS-03: with the app open and no refresh, a status change via the API updates the row via `ShipmentUpdated`; a new shipment appears as a new row; the indicator reflects connection state.

#### Screen O2 — Timeline drawer (OPS-04)
- **Layout:** fixed right-side panel, 400px wide, full height, white over a semi-transparent backdrop (`rgba(0,0,0,0.3)`); header (`#f8f9fa`, `md` padding): tracking number (weight 600) + close `×` button (`aria-label="Close"`, text-only fallback for screen readers); body: timeline identical to portal P2 (rows: created / status-changed with badge, `lg` row padding, right-aligned timestamps, `occurredAt` ascending).
- **Data source:** on open: `GET {trackingApiUrl}/api/tracking/{n}/events`. Live: while open, each `ShipmentUpdated` for that number triggers a timeline re-fetch (D5).
- **Interaction:** open: join tracking group (`JoinTrackingGroup(n)`) + fetch. Close (× or backdrop click): leave group (`LeaveTrackingGroup(n)`) + destroy. The persistent app-level connection is untouched (D4).
- **States:** loading (spinner, `Loading timeline…`); empty (`No events yet — …`); error (inline `alert` with `Retry`); populated (live-updating).
- **Acceptance (OPS-04):** opening the drawer shows the full event timeline parsed from `payloadJson`; a status change while open re-fetches and the drawer updates without any user action; closing leaves the group; opening two drawers sequentially never leaks group subscriptions (one group active at a time).

### Shared timeline rendering rules (portal P2 + drawer O2)
1. Sort by `occurredAt` ascending.
2. `shipment.created` → `Shipment created` + description/destination sub-line from `payloadJson`.
3. `shipment.status.changed` → `Status changed to {status}` + badge.
4. Unknown `eventType` → render `{eventType}` as the label (no crash).
5. `payloadJson` parse failure → label from `eventType`, no sub-line.
6. Timestamps `yyyy-MM-dd HH:mm`.
