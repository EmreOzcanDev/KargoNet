Stand up the Tracking.Api persistence layer and the idempotent event-apply pipeline: the `ShipmentTracking` / `TrackingEvent` / `ProcessedEvent` entities, `TrackingDbContext` (Npgsql) + design-time factory + `InitialCreate` migration; the `ShipmentEventsConsumer` delivery pipeline over the Phase 2 `IConsumerBroker` seam (two event types, unknown -> failure, retry/DLQ routing, always ack — mirroring `ConsumerBase`'s contract exactly, per D1); and the `ShipmentEventHandler` idempotent apply (one EF transaction: ProcessedEvents check by EventId, upsert `ShipmentTracking`, insert `TrackingEvent`, insert `ProcessedEvent`; concurrent-duplicate `DbUpdateException` treated as already-processed, per D2). <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| broker -> consumer | Untrusted message bodies cross from the broker into `ShipmentEventsConsumer.HandleDeliveryAsync`; a malformed body must not crash the host or leak a stack to a client |
| consumer -> EF | Deserialized event fields (tracking number, status, payload JSON) are persisted into the read model; unbounded/absent fields must not corrupt rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `ShipmentEventsConsumer.HandleDeliveryAsync` | medium | mitigate | Malformed body / unknown event type / unparseable `x-retry-count` are treated as handler failures and routed to retry then DLQ; the consumer always acks and never propagates a broker-parsed exception to the host (mirrors `ConsumerBase`) |
| T-04-02 | Tampering | `ShipmentEventHandler.ApplyCoreAsync` | medium | mitigate | Event fields are written only inside a single EF transaction behind the `ProcessedEvents` EventId check; a `DbUpdateException` on the `ProcessedEvent` PK is treated as an already-processed duplicate (success), preventing a redelivery from double-applying (TRK-01) |
| T-04-03 | Information Disclosure | `ShipmentEventHandler` post-apply side effects | low | accept | Cache-delete and broadcast failures are logged and swallowed, never rethrown, so a side-effect failure cannot turn an applied event into a broker retry loop |
| T-04-SC | Tampering | EF Core / Npgsql package install | high | mitigate | Packages are pinned explicitly (`Microsoft.EntityFrameworkCore* 10.0.15`, `Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3`) and must appear in `dotnet list package` output before the migration step; no live database is contacted at design time |
