| Boundary | Description |
|----------|-------------|
| client -> SignalR hub | A client joins a tracking-number group; the tracking number becomes a SignalR group key |
| broker -> consumer | Untrusted broker deliveries cross into the hosted consume loop and the plan 04-01 pipeline |
| broadcaster -> clients | The applied update DTO is pushed to all clients and to the tracking-number group |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Information Disclosure | `SignalRShipmentUpdateBroadcaster` | medium | accept | The broadcast sends only the already-published `TrackingUpdatedDto` (no secrets); it is an unauthenticated real-time surface per phase scope (no auth by design) |
| T-04-08 | Denial of Service | `ShipmentEventsConsumer.ExecuteAsync` | medium | mitigate | The consume loop catches connection/consume failures, logs, and retries on a 2-second backoff without throwing, so a broker blip cannot crash the host; deliveries are always acked by the plan 04-01 pipeline |
| T-04-09 | Tampering | `RabbitConsumerBroker.ConsumeAsync` | low | accept | `BasicConsume` runs with `autoAck: false`, so messages are only acknowledged after the plan 04-01 handler completes; no broker-returned data is trusted beyond the `EventSerializer` deserialize + ack |
| T-04-SC | Tampering | RabbitMQ.Client 7.2.2 consumption path | high | accept | No new package is introduced by this plan (RabbitMQ.Client 7.2.2 is already pinned in `KargoNet.Messaging` from Phase 2 / plan 04-02); `RabbitConsumerBroker` is a new file that reuses the existing pin and the plan 04-02 `LazyChannelFactory` |
