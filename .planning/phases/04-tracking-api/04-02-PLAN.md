<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> tracking endpoint | Untrusted tracking number arrives in the URL path; it is used to build a Redis key and an EF query |
| client -> DLQ admin endpoint | An operator can trigger a DLQ replay that republishes broker messages back to the main exchange |
| API -> Redis / broker | The API opens lazy connections to Redis and RabbitMQ; a missing backend must not block startup |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-04 | Tampering | `TrackingEndpoints` cache key | low | accept | The tracking number is lowercased into the fixed `tracking:{number}` key prefix; no interpolation into a query — it is an EF parameter and a single Redis key, so path input cannot inject |
| T-04-05 | Denial of Service | `RabbitDlqAdmin.ReplayAsync` | medium | mitigate | Replay is an operator-initiated, bounded `BasicGet` loop returning the moved count; each republished message drops the `x-retry-count` header so a poison message re-enters the normal retry->DLQ path rather than looping |
| T-04-06 | Denial of Service | `LazyRedisConnection` / `LazyChannelFactory` | medium | mitigate | Both connections are lazy (SemaphoreSlim-guarded) and only open on first use, so the API starts and serves the InMemory/endpoint tests with no reachable Redis or broker (live backends are a Phase 6 deferral) |
| T-04-SC | Tampering | StackExchange.Redis package install | high | mitigate | The package is added with no `-v` and the resolved 2.x version is recorded and verified present in `dotnet list package` before the endpoint wiring; only the latest stable 2.x line is acceptable |
</threat_model>
