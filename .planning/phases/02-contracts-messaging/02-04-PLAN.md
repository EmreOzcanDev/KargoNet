<objective>
Implement the hand-built retry/DLQ consumer in KargoNet.Messaging. Extract the retry/DLQ routing choice as a pure function — `RetryPolicy.Decide(attemptCount, exception) → { RepublishToRetry, RouteToDlq }` — and build `ConsumerBase<T>` around a small `IConsumerBroker` seam: consume from `shipments.main` (prefetch 1), ack on handler success; on failure, decide via `RetryPolicy` and republish to the retry queue (`shipment.retry`) with an incremented `x-retry-count` plus original headers + `x-exception` (attempts below 3), or to the DLQ (`shipment.dead`) with `x-exception` (attempts ≥ 3), then ack the original in every case. The pure decision function and the header manipulation are unit-tested with a fake broker — no live broker.

Purpose: MSG-02/MSG-03 (SC3/SC4) are the reliability core — bounded retry via `x-retry-count` and dead-letter routing with `x-exception`. Isolating the decision as a pure function means the whole retry/DLQ behavior is provable now, with only the live consume/requeue loop deferred to Phase 6.

Output: `RetryPolicy` + `RetryDecision`, the `IConsumerBroker` seam, `ConsumerBase<T>`, and unit tests of the decision boundary, header manipulation, and the full ack/retry/DLQ flow against a fake broker.
</objective>

  <action>
Create the consuming files under `src/BuildingBlocks/KargoNet.Messaging/Consuming/` in `KargoNet.Messaging.Consuming`. Reuse `RabbitTopology` constants (from 02-02) for the exchange and routing keys, and `EventSerializer` (from 02-01) to deserialize the envelope payload. No new package references.

1. `RetryDecision.cs` — a discriminated result type with two cases: `RepublishToRetry(int newRetryCount)` and `RouteToDlq`. Keep it a small public record/struct.

2. `RetryPolicy.cs` — the PURE decision function, no broker, no IO. `static RetryDecision Decide(int currentRetryCountHeader, Exception exception)`:
   - `currentRetryCountHeader` is the value of the incoming `x-retry-count` header (0 when absent — the first delivery).
   - Derive the current attempt as `currentRetryCountHeader + 1` (first delivery = attempt 1).
   - If the current attempt is below 3 (i.e. attempts 1 and 2): return `RepublishToRetry` with `newRetryCount = currentRetryCountHeader + 1`.
   - If the current attempt is 3 or more: return `RouteToDlq`.
   This matches the locked semantics: republishes happen for attempts 1 and 2; a third failed attempt goes to the DLQ.

3. `IConsumerBroker.cs` — the small broker seam for the consumer: `Task AckAsync(ulong deliveryTag)` and `Task PublishAsync(string exchange, string routingKey, ReadOnlyMemory<byte> body, IDictionary<string, object?>? headers)`. (The real `IChannel`-backed adapter is written in Phase 6 alongside the live consume loop; only the seam is needed here.)

4. `ConsumerBase.cs` — `ConsumerBase<T>` (generic over the payload type). It is constructed with an `IConsumerBroker`, a handler `Func<EventEnvelope<T>, Task>`, and the main-queue consume setup. Its delivery pipeline:
   - Deserialize the delivery body into `EventEnvelope<T>` via `EventSerializer`.
   - On handler success: `AckAsync(deliveryTag)`.
   - On handler failure: read `x-retry-count` from the headers (default 0), call `RetryPolicy.Decide`, then:
     - `RepublishToRetry`: build new headers = original headers + `x-retry-count = newRetryCount` + `x-exception = <exception message>`; `PublishAsync(exchange, RabbitTopology.RetryRoutingKey, body, newHeaders)`; then `AckAsync(deliveryTag)`.
     - `RouteToDlq`: build new headers = original headers + `x-exception = <exception message>`; `PublishAsync(exchange, RabbitTopology.DlqRoutingKey, body, newHeaders)`; then `AckAsync(deliveryTag)`.
   - `nack`/requeue is NEVER used — every failure path ends by acking the original.

The consume-from-main-queue loop (`BasicConsumeAsync`, prefetch 1) may be a thin method that binds the delivery pipeline to the broker; the pipeline itself is what is unit-tested via the seam.

|-----------|----------|-----------|----------|-------------|-----------------|

| T-02-08 | Repudiation | ConsumerBase ack-after-republish | high | mitigate | Every failure path republishes to retry/DLQ and then acks the original (never requeues), so a message is never lost between attempts; ack-on-every-path is asserted by ConsumerBaseTests |
