<objective>
Implement the outbox publisher and complete the DI wiring in Shipment.Api. `OutboxPublisherService : BackgroundService` polls `WHERE Status = Pending ORDER BY CreatedAt LIMIT 50` every 2 s; per row it publishes the stored `PayloadJson` verbatim to routing key `shipment` through the Phase 2 `MessagePublisher` (publisher confirms); on confirm it marks the row `Published` + `PublishedAt` in its own short transaction; on any failure (`PublishNotConfirmedException` or broker error) it logs and leaves the row `Pending` for the next poll — never deletes. Purpose: SC4 — pending outbox rows reliably reach RabbitMQ with confirms, surviving broker downtime by staying pending until confirmed.

Output: `OutboxPublisherService`, the completed `Program.cs` DI wiring, and `OutboxPublisherServiceTests` covering publish-and-mark, failure-leaves-pending, skip-published, and batch-size behavior.
</objective>

1. Create `src/Services/Shipment.Api/Publishing/OutboxPublisherService.cs` (namespace `KargoNet.Shipment.Api.Publishing`), `OutboxPublisherService : BackgroundService`. Constructor takes `ShipmentDbContext`, `MessagePublisher`, and an `ILogger<OutboxPublisherService>`.
   - Expose a public `Task<int> PollOnceAsync(CancellationToken ct)` (the directly-drivable poll; returns the number of rows published) that:
     - queries `dbContext.Set<OutboxMessage>().Where(o => o.Status == OutboxStatus.Pending).OrderBy(o => o.CreatedAt).Take(50)`;
     - per row: `await publisher.PublishAsync(RabbitTopology.ShipmentRoutingKey, row.PayloadJson UTF-8 bytes, null)` — the stored envelope JSON is published VERBATIM, never re-serialized;
     - on success: open a short transaction, set `Status = Published` + `PublishedAt = now`, `SaveChanges`, commit — one row per own transaction so a single failure cannot block the rest of the batch;
     - on any exception (`PublishNotConfirmedException` or broker error): log it, leave the row `Pending`, and CONTINUE with the next row. Never delete a row on failure.
   - `ExecuteAsync(CancellationToken stoppingToken)` loops `await PollOnceAsync(stoppingToken); await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);` until `stoppingToken` is cancelled — respecting host shutdown. Keep `PollOnceAsync` free of any delay/timer logic so tests drive it directly.

2. Add a ProjectReference from `src/Services/Shipment.Api/Shipment.Api.csproj` to `src/BuildingBlocks/KargoNet.Messaging/KargoNet.Messaging.csproj` if not already present (Shipment.Api currently references only KargoNet.Contracts).

3. Create `src/BuildingBlocks/KargoNet.Messaging/Publishing/LazyOutboxChannelFactory.cs`: a small component implementing `IOutboxChannel` (the seam `MessagePublisher` already consumes) whose `RabbitMQ.Client.IChannel` is created on FIRST publish (connection + channel opened on demand, cached afterwards), and whose `PublishAsync` is async. This is what makes "the API starts without a reachable broker" true — nothing connects at startup; a missing/unreachable broker surfaces as a publish exception, which `PollOnceAsync` catches and converts into leave-pending. Register `IOutboxChannel` → `LazyOutboxChannelFactory` (singleton) in DI.
